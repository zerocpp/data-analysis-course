建议先确认虚拟化已开启：

## 安装 Ubuntu 22.04 LTS

执行：

```powershell
wsl --install -d Ubuntu-22.04
```

如果你的 Windows / WSL 使用的是新版语法，也可能支持：

```powershell
wsl --install Ubuntu-22.04
```

我建议用第一种，兼容性更好：

```powershell
wsl --install -d Ubuntu-22.04
```

Microsoft 官方文档说明，`wsl --install -d <Distro>` 可以指定要安装的 Linux 发行版；如果没指定，默认会安装 Ubuntu。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/install))

如果下载卡在 0% 或 Microsoft Store 下载异常，试试：

```powershell
wsl --install --web-download -d Ubuntu-22.04
```

Microsoft 文档也给出过这个处理方式：如果安装卡在 0.0%，可以加 `--web-download -d <DistroName>`。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/install))

------

## 把这个 WSL 设置成默认 root + systemd

在 root 里面执行：

```bash
cat > /etc/wsl.conf <<'EOF'
[boot]
systemd=true

[user]
default=root
EOF

cat /etc/wsl.conf
```

Microsoft 的 WSL 配置文档说明，`/etc/wsl.conf` 是每个发行版自己的配置文件，可以配置 systemd 和默认用户；`[user] default=...` 用来指定 WSL 会话启动时使用哪个用户 。Docker 专用入口也正是用 `-u root` 进入 `/root/workspace` 并启动 Docker 服务

### 策略二：使用 Ubuntu 仓库安装 Docker🐳 

你现在要走的是 **Ubuntu 仓库版 Docker**，不添加 Docker 官方源，也不写 `/etc/apt/sources.list.d/docker.sources`。

Ubuntu 官方包页面也显示 Ubuntu 22.04 Jammy 仓库里有 `docker.io` 包，属于 `universe` 组件。([Ubuntu 软件包搜索](https://packages.ubuntu.com/jammy/docker.io))

先执行这一整段：

```bash
# 1. 如果之前添加过 Docker 官方源，先删除，避免混用
rm -f /etc/apt/sources.list.d/docker.list
rm -f /etc/apt/sources.list.d/docker.sources
rm -f /etc/apt/keyrings/docker.asc
rm -f /etc/apt/keyrings/docker.gpg

# 2. 清理 apt 缓存并更新
apt-get clean
apt-get update

# 3. 确保 universe 仓库可用
apt-get install -y software-properties-common
add-apt-repository -y universe

# 4. 再更新一次
apt-get update

# 5. 查看 Ubuntu 仓库里 Docker 包是否可用
apt-cache policy docker.io docker-compose-v2 docker-compose

# 6. 使用 Ubuntu 仓库安装 Docker 和 Compose v2
apt-get install -y docker.io docker-compose-v2

# 7. 启动 Docker 服务
systemctl enable --now docker

# 8. 验证
systemctl status docker --no-pager
docker version
docker compose version
docker ps
```

# 6. 编写 Task

Task 就是一道**可执行、可验证的数据分析题**。

一个 Task 至少需要保证：

- 问题描述清楚；
- 数据足以回答问题；
- 答案唯一；
- 主要考察一种明确的数据分析能力；
- 不依赖学生个人电脑上的额外文件；
- 可以通过标准答案程序验证。

设计时优先问自己：

```text

    ↓
需要进行什么分析？
    ↓
最终答案的数据类型是什么？
    ↓
是否只有一个正确答案？
```

不要只追求题目“难”，更重要的是题目能够被准确理解和稳定评测。

# 8. 编写标准答案程序 reference.py

`reference.py` 用来计算该 Task 的正确答案。

它不是“答案说明”，而是**可执行的标准答案程序**。

要求：

- 可以独立运行；
- 能读取 Task 所需数据；
- 输出唯一答案；
- 结果稳定；
- 不依赖学生个人环境；
- 不访问本机私有文件；
- 不使用随机结果作为最终答案。

最重要的是：

```text
同一份 Task + 同一份 Data
        ↓
reference.py
        ↓
唯一 Ground Truth
```

编写完成后先自行执行：

```bash
python reference.py
```

确认没有异常，并记录最终输出的数据类型和格式。

# 9. 编写 Agent

Agent 是你编写的自动解题程序。

Agent 应根据：

```text
Task
 +
Data
```

完成数据分析并返回最终答案。

课程接口**以当前课程模板为准**，不要自行修改函数名、输入协议或输出协议。

Agent 的重点不是写死某一道题的答案，而是完成课程模板要求的数据读取、任务理解、分析和返回过程。

建议至少检查：

- Agent 是否能读取数据；
- 是否正确理解问题；
- 是否正确识别字段；
- 是否正确处理数据类型；
- 是否执行了正确的统计/分析逻辑；
- 最终输出是否符合课程要求的数据类型。

# 10. Failure Mode（错误类型）

Failure Mode 表示：

> 你认为 Agent 在完成该 Task 时最可能出现哪类错误。

例如：

- 需求理解错误；
- 字段理解错误；
- 数据类型错误；
- 过滤条件错误；
- 分组或聚合错误；
- 统计计算错误；
- 输出格式错误。

填写时必须使用课程提供的 **FM 编号**。

| 代码 | 失败模式             | 完整键（`task.json` 填这个）        |
| ---- | -------------------- | ----------------------------------- |
| FM01 | 需求理解偏差         | `FM01_REQUIREMENT`                  |
| FM02 | Schema 理解错误      | `FM02_SCHEMA`                       |
| FM03 | 数据类型处理错误     | `FM03_DATA_TYPE`                    |
| FM04 | 筛选或排序错误       | `FM04_FILTER_SORT`                  |
| FM05 | Join / 关联错误      | `FM05_JOIN`                         |
| FM06 | 聚合口径错误         | `FM06_AGGREGATION`                  |
| FM07 | 时间与时区错误       | `FM07_TIME_TIMEZONE`                |
| FM08 | 缺失值处理错误       | `FM08_MISSING_VALUE`                |
| FM09 | 异常值或边界处理错误 | `FM09_OUTLIER_BOUNDARY`             |
| FM10 | 重复记录处理错误     | `FM10_DUPLICATE_RECORD_HANDLING`    |
| FM11 | 规划与分解错误       | `FM11_PLANNING_DECOMPOSITION`       |
| FM12 | 验证不足             | `FM12_VERIFICATION`                 |
| FM13 | 数值精度与舍入错误   | `FM13_NUMERICAL_PRECISION_ROUNDING` |
| FM14 | 提示注入或不可信数据 | `FM14_PROMPT_INJECTION`             |

不要自行创建与课程编号体系不一致的新编号。

Failure Mode 的作用不是给 Agent “判分”，而是帮助你在设计阶段形成一个可验证的失败假设：

```text
我设计的 Task
      ↓
Agent 可能在哪里出错？
      ↓
实际运行时是否真的发生？
      ↓
为什么发生？
      ↓
Task / Agent 应该怎样改进？
```

# 12. 理解运行结果

本地测试结果可以先分成三类。

### (1)正确完成

Agent 正常执行，并且最终输出与标准答案一致。

重点不是只看“运行成功”，还要确认：

```text
Agent Output == Ground Truth
```

---

### (2)答案错误

Agent 程序正常运行，但最终答案错误。

此时重点分析：

- 是否理解错题目；
- 是否选择错字段；
- 是否漏掉过滤条件；
- 是否出现数据类型转换错误；
- 是否使用了错误的统计方法；
- 是否输出格式不符合要求。

---

### (3)运行失败

程序或模型调用没有正常完成。

常见检查方向：

- Python 异常；
- 文件路径错误；
- 数据文件不存在；
- API 调用失败；
- Agent 接口不符合模板；
- 输出没有正常返回；
- Docker / 本地课程服务没有启动。

# 17. 常见问题速查

## Q1：Docker 服务没有启动怎么办？

```bash
systemctl start docker.service
systemctl status docker --no-pager
```

---

## Q2：`docker compose` 不存在怎么办？

先执行：

```bash
docker compose version
```

如果不存在，再检查：

```bash
docker-compose version
```

如果旧版 `docker-compose` 可以正常输出，则说明当前安装的是 Compose v1。课程发布包如果要求 Compose v2，应优先按照前文安装 Compose v2。

## Q3：`run` 失败怎么办？

优先检查：

```bash
ls -lah workspace/my_task
python workspace/my_task/reference.py
```

然后确认：

- `task.json` 是否存在；
- 数据文件名是否正确；
- `reference.py` 是否可以独立运行；
- `agent.py` 是否符合课程接口；
- API 配置是否正确；
- 课程服务是否启动。

---

## Q6：Agent 能运行，但是答案错误怎么办？

这通常不是“环境安装问题”，而是数据分析逻辑问题。

按顺序检查：

```text
1. Task 是否理解正确
2. 字段是否选择正确
3. 数据类型是否正确
4. 过滤条件是否完整
5. 分组 / 聚合是否正确
6. 最终输出类型和格式是否正确
```

---

## Q7：reference.py 和 Agent 的答案不同，应该相信谁？

先检查 `reference.py` 本身是否真正符合 Task 定义。

标准答案程序必须满足：

```text
Task 定义正确
      +
Data 支持
      +
reference.py 逻辑正确
      ↓
唯一 Ground Truth
```

如果 reference.py 本身错误，应先修复标准答案程序，而不是为了“通过测试”去让 Agent 模仿错误答案。
