## 获取 API Key

1. 登录 [阿里云大学](https://university.aliyun.com/)
2. 进入 [百炼控制台](https://bailian.console.aliyun.com/) 获取免费配额
3. 在 API Key 管理页面创建密钥

业务空间 ID决定了你的BaseURL格式

你已经创建的是 **华北 2（北京）的百炼按量计费 API Key**，那么你的 OpenAI 兼容 BaseURL 格式就是：

```
https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
```

把 `{WorkspaceId}` 替换成你的真实 **业务空间 ID** 即可。阿里云官方文档明确说明，华北 2（北京）的按量计费 Base URL 是这个格式，且需要用真实业务空间 ID 替换 `WorkspaceId`。

## **如何找到你的 WorkspaceId**

进入 **阿里云百炼控制台**，确认右上角地域是 **华北 2（北京）**，然后进入 **业务空间管理**，在列表里的 **Workspace ID** 列复制你 API Key 所属业务空间的 ID。官方文档说明：登录百炼控制台后，进入业务空间管理界面，在 `Workspace ID` 列查看并复制对应业务空间 ID。

也就是说，假设你的 Workspace ID 是：llm-abc123

那么你的 BaseURL 就是：https://llm-abc123.cn-beijing.maas.aliyuncs.com/compatible-mode/v1

# 第一步. 前提确认

适用系统：**Windows 11** 或 **Windows 10 版本 2004 及以上，Build 19041 及以上**。Microsoft 官方 WSL 安装文档说明，下面的 `wsl --install` 命令要求 Windows 10 version 2004+ / Build 19041+ 或 Windows 11。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/install))

建议先确认虚拟化已开启：

1. 打开任务管理器。

2. 进入 **性能 → CPU**。

3. 看右下角 **虚拟化** 是否为 **已启用**。


Ubuntu 官方 WSL 文档也提醒：WSL 需要启用虚拟化，`wsl --install` 会尝试启用 Virtual Machine Platform，但通常需要重启后生效。([Ubuntu Documentation](https://documentation.ubuntu.com/wsl/stable/howto/install-ubuntu-wsl2/))

```bash
PowerShell
```

```text
以管理员身份运行
```

## 更新 WSL 

先执行：

```bash
wsl --update
```

再查看 WSL 版本：

```bash
wsl --version
```

Microsoft WSL 基础命令文档说明，`wsl --update` 用于更新 WSL，`wsl --version` 用于查看 WSL 及其组件版本。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands))

## 查看可安装的 Ubuntu 版本

执行：

```bash
wsl --list --online
```

也可以写成：

```bash
wsl -l -o
```

你要找的是：

```bash
Ubuntu-22.04    Ubuntu 22.04 LTS
```

Ubuntu 官方 WSL 文档示例中，可安装列表包含 `Ubuntu-22.04 Ubuntu 22.04 LTS`，并说明可以用列表里的 `NAME` 安装指定版本。([Ubuntu Documentation](https://documentation.ubuntu.com/wsl/stable/howto/install-ubuntu-wsl2/))

用管理员 PowerShell 执行：

```bash
ipconfig /flushdns
netsh winsock reset
netsh winhttp reset proxy
```

执行完后重启电脑，再试：

```bash
wsl --list --online
```

## 安装 Ubuntu 22.04 LTS

执行：

```powershell
wsl --install -d Ubuntu-22.04
```

如果你的 Windows / WSL 使用的是新版语法，也可能支持：

```powershell
wsl --install Ubuntu-22.04
```

我建议用第一种，兼容性更好：

```powershell
wsl --install -d Ubuntu-22.04
```

Microsoft 官方文档说明，`wsl --install -d <Distro>` 可以指定要安装的 Linux 发行版；如果没指定，默认会安装 Ubuntu。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/install))

如果下载卡在 0% 或 Microsoft Store 下载异常，试试：

```powershell
wsl --install --web-download -d Ubuntu-22.04
```

Microsoft 文档也给出过这个处理方式：如果安装卡在 0.0%，可以加 `--web-download -d <DistroName>`。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/install))

------

## 重启 Windows

安装完成后，按提示重启电脑。

重启后，再打开 PowerShell，执行：

```bash
wsl -l -v
```

出现类似：

```bash
  NAME            STATE           VERSION
* Ubuntu-22.04    Stopped         2
```

Microsoft 文档说明，可以用 `wsl --list --verbose` / `wsl -l -v` 查看已安装发行版及其 WSL 版本。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands))

------

## 如果 Ubuntu-22.04 不是 VERSION 2，改成 WSL2

如果你看到：

```text
Ubuntu-22.04    Stopped    1
```

执行：

```powershell
wsl --set-version Ubuntu-22.04 2
```

并把以后新装的发行版默认设为 WSL2：

```powershell
wsl --set-default-version 2
```

Microsoft 文档说明，`wsl --set-version <distribution name> <versionNumber>` 可以把某个发行版设置为 WSL 1 或 WSL 2，`wsl --set-default-version 2` 可以把新发行版默认设为 WSL2。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands))

### 7. 设置默认 Ubuntu 发行版

------

## 用 root 进入 Ubuntu

在 **PowerShell** 执行：

```bash
wsl -d Ubuntu-22.04 -u root
```

进入后执行：

```bash
whoami
```

应该输出：

```bash
root
```

Microsoft 文档说明，可以用 `wsl --distribution <Distribution Name> --user <User Name>` 指定发行版和用户进入，例如指定 `root`；如果用户不存在才会报错，而 `root` 是 Linux 里默认存在的用户。

------

## 把这个 WSL 设置成默认 root + systemd

在 root 里面执行：

```bash
cat > /etc/wsl.conf <<'EOF'
[boot]
systemd=true

[user]
default=root
EOF

cat /etc/wsl.conf
```

Microsoft 的 WSL 配置文档说明，`/etc/wsl.conf` 是每个发行版自己的配置文件，可以配置 systemd 和默认用户；`[user] default=...` 用来指定 WSL 会话启动时使用哪个用户 。Docker 专用入口也正是用 `-u root` 进入 `/root/workspace` 并启动 Docker 服务

### 为后续 Docker Engine 做准备：启用 systemd

DataChallenging 本地课程环境采用 **WSL Ubuntu 内的 Docker Engine** 运行方式，不依赖 Docker Desktop，所以建议现在就启用 `systemd`。目标是在 WSL 内安装 Docker Engine 与 Compose 插件。

先在 Ubuntu 里检查：

```bash
ps -p 1 -o comm
```

如果输出已经是：

```text
systemd
```

这一步可以跳过。

如果不是，执行：

```bash
sudo tee /etc/wsl.conf > /dev/null <<'EOF'
[boot]
systemd=true
EOF
```

然后退出 Ubuntu：

```bash
exit
```

回到 **Windows PowerShell**，执行：

```powershell
wsl --shutdown
wsl -d Ubuntu-22.04/wsl -d Ubuntu
```

再检查：

```bash
ps -p 1 -o comm=
```

Microsoft WSL 配置文档说明，启用 systemd 需要在 `/etc/wsl.conf` 中加入 `[boot] systemd=true`，然后从 PowerShell 执行 `wsl.exe --shutdown` 重启 WSL 实例。([Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/wsl-config))

```
告诉系统“要算什么”

data.csv
    ↓
提供真实数据

reference.py
    ↓
按照确定的方法算出正确答案
    ↓
Gold Answer

agent.py
    ↓
让你的 Agent 自己理解题目、分析 CSV
    ↓
Agent Answer
```

最后平台比较：

```
Agent Answer
      vs
Gold Answer
```

判断 Agent 是否正确。

#### 2. 标准答案程序(  `reference.py`)说明

#### reference.py：这道题的“标准答案”

`reference.py` 的任务只有一个：

> **给定数据，稳定地计算出这道 Task 的正确结果。**

它不是智能 Agent，也不需要“理解”题目。

典型形式可以理解为：

```
def reference(df):
    ...
    return {"answer": ...}
```

它只依赖：

```
CSV 数据
```

然后严格按照题目要求进行：

```
筛选
→ 计算
→ 聚合
→ 排序
→ 输出正确答案
```

#### reference.py 最重要的要求

它必须：

```
简单
明确
确定
可验证
```

也就是说：

> 同一份数据运行多少次，都应该得到完全相同的答案。

因此 `reference.py`：

- 不使用 LLM；
- 不依赖随机行为；
- 不需要复杂容错；
- 不应该隐藏错误；
- 应直接实现题目规定的计算逻辑。

例如：

```
题目：
统计 status="failed" 的记录数

reference.py：
df[df["status"] == "failed"].shape[0]
```

越直接越好。

#### 3. 解题程序文件(`  agent.py`)说明

##### agent.py：你真正要设计和改进的东西

`agent.py` 则完全不同。

它面对的不只是自己设计的这一道题，而应该能够处理：

> **不同题目 + 不同 CSV 数据。**

可以把它理解成：

```
                ┌───────────────┐
Task ─────────→ │               │
                │   agent.py    │ ─────→ Answer
CSV ──────────→ │               │
                │               │
LLM ──────────→ │               │
                └───────────────┘
```

Agent 需要自己完成：

```
理解问题
   ↓
理解数据字段
   ↓
制定分析步骤
   ↓
读取和处理数据
   ↓
进行计算
   ↓
检查结果
   ↓
输出最终答案
```

因此它才是这门课程真正要测试的对象。

#### 4. 课程要求设计程序文件

在阶段一，你同时扮演两个角色：

```
Task Designer
+
Agent Developer
```

所以你需要完成：

```
Task v1
├── task.json
├── data.csv
└── reference.py

Agent v1
└── agent.py
```

也就是说，你既要：

> **出一道数据分析题**

又要：

> **给这道题提供一份正确的标准答案**

同时还要：

> **设计一个 Agent 来尝试解决数据分析任务。**

Phase 2 中，同学会收到来着其他人的匿名 Task。

他们应该看到的是：

```
题目
+
数据
```

而不能看到：

```
标准答案
```

否则挑战就失去意义了。

因此概念上：

```
你的 Task
├── task.json       → 可以匿名分发
├── data.csv        → 可以匿名分发
└── reference.py    → 私有，不发给 Reviewer
```

Reviewer 会使用：

```
自己的 agent.py
```

来解决你的匿名 Task。

因此：

```
你的 reference.py
        ↓
教师 / 平台私有 Gold

别人的 agent.py
        ↓
挑战你的匿名 Task
```

```
                  Task + CSV
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
   reference.py             agent.py
          │                     │
          ▼                     ▼
    Gold Answer            Agent Answer
          │                     │
          └─────────┬───────────┘
                    ▼
                  Compare
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
        Correct             Wrong
                              │
                              ▼
                      Failure Diagnosis
                              │
                              ▼
                        14种Failure Mode
```

#### reference.py

目标是：

> **把正确答案写清楚。**

应该：

```
短
直接
确定
容易人工检查
```

不要：

```
调用 LLM
加入随机逻辑
针对运行环境做复杂判断
大量 try/except 掩盖错误
```

可以把它理解成：

> **老师手里的标准答案。**

#### agent.py

目标是：

> **构建一个尽可能通用的数据分析 Agent。**

应该考虑：

```
如何理解 Task
如何理解 CSV
如何规划分析步骤
如何调用 LLM
如何验证计算结果
如何控制 Token
如何满足输出格式
如何处理失败
```

尤其不能：

```
if 当前 data.csv:
    return 已知答案
```

也就是不能针对自己的数据直接写死答案。

因为第二阶段它要面对的是：

```
10 个完全陌生的 Task
```

写死自己 Task 的答案没有任何意义。

两者最大的运行差异

| 维度                   | `reference.py`            | `agent.py`                    |
| ---------------------- | ------------------------- | ----------------------------- |
| 输入                   | 数据                      | Task + 数据 + LLM             |
| LLM                    | 禁止使用                  | 可以使用                      |
| 确定性                 | 必须确定                  | 可以存在 LLM 随机性           |
| Token 消耗             | 不使用 Token Budget       | LLM 调用消耗课程 Token Budget |
| 资源约束               | 普通确定性执行            | 受时间、内存、Token 等限制    |
| 失败代表什么           | Task 的标准答案实现有问题 | Agent 的数据分析能力出现问题  |
| 是否是课程主要评价对象 | 否                        | **是**                        |

# 10. Failure Mode（失败模式）

Failure Mode 表示：

> 你认为 Agent 在完成该 Task 时最可能出现哪类错误。

例如：

- 需求理解错误；
- 字段理解错误；
- 数据类型错误；
- 过滤条件错误；
- 分组或聚合错误；
- 统计计算错误；
- 输出格式错误。

填写时必须使用课程提供的 **FM 编号**。

| FM 编号                           | 中文名称             | 含义说明                                                   |
| --------------------------------- | -------------------- | ---------------------------------------------------------- |
| `FM_REQUIREMENT`                  | 需求理解偏差         | Agent 误解任务目标、条件或输出要求。                       |
| `FM_SCHEMA`                       | Schema 理解错误      | Agent 错误理解字段含义、主键、字段关系或数据粒度。         |
| `FM_DATA_TYPE`                    | 数据类型处理错误     | Agent 错误处理数值、字符串、日期、布尔值等数据类型。       |
| `FM_FILTER_SORT`                  | 筛选或排序错误       | Agent 使用了错误的筛选条件、排序字段、排序顺序或方向。     |
| `FM_JOIN`                         | Join / 关联错误      | Agent 使用了错误的关联字段或 Join 方式。                   |
| `FM_AGGREGATION`                  | 聚合口径错误         | Agent 在求和、平均、分组统计等过程中使用了错误的计算口径。 |
| `FM_TIME_TIMEZONE`                | 时间与时区错误       | Agent 错误处理日期、时间范围、时间窗口或时区。             |
| `FM_MISSING_VALUE`                | 缺失值处理错误       | Agent 错误识别或处理 NaN、null、空字符串等缺失数据。       |
| `FM_OUTLIER_BOUNDARY`             | 异常值或边界处理错误 | Agent 错误处理异常值、阈值或边界条件。                     |
| `FM_DUPLICATE_RECORD_HANDLING`    | 重复记录处理错误     | Agent 错误识别、保留、删除或统计重复记录。                 |
| `FM_PLANNING_DECOMPOSITION`       | 规划与分解错误       | Agent 的任务拆解或执行步骤顺序不合理。                     |
| `FM_VERIFICATION`                 | 验证不足             | Agent 未对中间结果或最终结果进行必要检查。                 |
| `FM_NUMERICAL_PRECISION_ROUNDING` | 数值精度与舍入错误   | Agent 在数值精度、小数位或舍入方式上处理错误。             |
| `FM_PROMPT_INJECTION`             | 提示注入或不可信数据 | Agent 被数据中的不可信指令或文本影响了正常分析行为。       |

FM 编号作为系统Failure Mode 的唯一标识，强调不要自行创建与课程编号体系不一致的新编号。

Failure Mode 的作用不是给 Agent “判分”，而是帮助你在设计阶段形成一个可验证的失败假设：

```text
我设计的 Task
      ↓
Agent 可能在哪里出错？
      ↓
实际运行时是否真的发生？
      ↓
为什么发生？
      ↓
Task / Agent 应该怎样改进？
```

# 12. 理解运行结果

本地测试结果可以先分成三类。

### (1)正确完成

Agent 正常执行，并且最终输出与标准答案一致。

重点不是只看“运行成功”，还要确认与reference.py执行结果：

```text
Agent Output == Ground Truth
```

Agent 执行结果：Agent Output

reference.py执行结果：Ground Truth

---

### (2)答案错误

Agent 程序正常运行，但最终答案错误。

此时重点分析：

- 是否理解错题目；
- 是否选择错字段；
- 是否漏掉过滤条件；
- 是否出现数据类型转换错误；
- 是否使用了错误的统计方法；
- 是否输出格式不符合要求。

---

### (3)运行失败

程序或模型调用没有正常完成。

常见检查方向：

- Python 异常；
- 文件路径错误；
- 数据文件不存在；
- API 调用失败；
- Agent 接口不符合模板；
- 输出没有正常返回；
- Docker / 本地课程服务没有启动。

> 经第二阶段测试与分析后，未发现当前 Task 存在必须调整的问题，因此 Task v2 保留 Task v1 的设计。

------

#### 二、Agent 设计与迭代

这一部分同样只讲：

> **Agent 是怎么设计的，以及从 v1 到 v2 有没有改变。**

##### 1. Agent v1 设计思路

说明第一阶段 Agent 的总体设计。

重点回答：

- Agent 如何理解 Task；
- Agent 如何使用 CSV 数据；
- Agent 如何进行数据分析；
- 是否使用 LLM；
- 大致的解题流程是什么；
- 你设计这个 Agent 时最关注什么能力。

例如可以概括成：

```
读取 Task
   ↓
理解题目要求
   ↓
分析 CSV Schema
   ↓
规划分析步骤
   ↓
执行数据分析
   ↓
检查结果
   ↓
输出答案
```

不需要把整个 `agent.py` 代码粘贴到实验报告。

实验报告要说明的是：

> **你的 Agent 为什么这样设计。**

------

#### 2. Agent v2 设计思路

说明第二阶段最终 Agent 的设计。

重点回答：

- Agent v2 最终采用什么思路；
- 是否针对 Phase 2 中观察到的问题做了调整；
- 最终希望解决 Agent v1 的什么不足。

如果没有修改，也完全允许。

此时必须明确写：

> **Agent v2 与 Agent v1 保持一致，本阶段未对 Agent 进行修改。**

同时简单说明你的判断理由。

------

#### 3. Agent v1 → Agent v2 的改变

如果进行了修改，重点说明：

```
Agent v1 出现什么问题
        ↓
你如何判断问题原因
        ↓
采取什么修改
        ↓
希望 Agent v2 改善什么
```

例如：

| 发现的问题        | Agent v1 | Agent v2   | 改进目的           |
| ----------------- | -------- | ---------- | ------------------ |
| Schema 理解不稳定 | 原策略   | 新策略     | 提高字段理解       |
| 缺少结果验证      | 直接输出 | 增加检查   | 降低错误答案       |
| 分析规划不足      | 一次完成 | 分步骤分析 | 提高复杂任务稳定性 |

这里也不要求一定修改。

如果没有修改，可以直接说明：

> 根据第二阶段的运行与分析结果，没有发现足够明确的问题需要修改 Agent，因此最终 Agent v2 保留 Agent v1 的实现。

------

#### 三、总结与反思

最后只需要进行总体总结，不再增加新的技术章节。

重点回答三个问题：

#### 1. 这次实验你学到了什么？

例如：

- 对数据分析 Task 设计有什么新的认识；
- 对 Agent 能力边界有什么认识；
- 什么样的问题容易让 Agent 失败；
- 如何判断一个 Agent 是否真正具有通用数据分析能力。

##### 2. 哪些设计经验以后可以继续使用？

例如：

```
Task 要有清晰目标
Reference 要可靠
Agent 要先理解 Schema
复杂任务需要分解
结果必须验证
```

重点总结**可迁移的经验**。

#### 3. 如果继续迭代，下一步准备优化什么？

这里写未来方向即可，例如：

- 提高 Agent 对复杂 Schema 的理解；
- 增强 Join 能力；
- 增加结果验证机制；
- 改进任务规划；
- 设计更有区分度的 Task；
- 增加边界数据和异常数据；
- 提高 Agent 的稳定性和 Token 使用效率。

------

### 最终实验报告结构

因此整份 Word 实验报告可以非常清楚地压缩成：

```
1. Task 设计与迭代
   1.1 Task v1 设计思路
   1.2 Task v2 设计思路
   1.3 Task v1 → Task v2 的改变
       （若无改变，明确写“未修改”并说明原因）

2. Agent 设计与迭代
   2.1 Agent v1 设计思路
   2.2 Agent v2 设计思路
   2.3 Agent v1 → Agent v2 的改变
       （若无改变，明确写“未修改”并说明原因）

3. 总结与反思
   3.1 实验收获
   3.2 可复用的设计经验
   3.3 后续优化方向
```

另外，**Task v2 / Agent v2 不强制必须发生修改**。如果第二阶段与第一阶段完全一致，也是允许的，但必须在实验报告相应位置明确写明“未修改，与 v1 保持一致”，并说明判断依据。

### Q2：`docker compose` 不存在怎么办？

先执行：

```bash
docker compose version
```

如果不存在，再检查：

```bash
docker-compose version
```

如果旧版 `docker-compose` 可以正常输出，则说明当前安装的是 Compose v1。课程发布包如果要求 Compose v2，应优先按照前文安装 Compose v2。

### Q3：`run` 失败怎么办？

如果是阶段一执行run失败优先检查：

```bash
ls -lah workspace/phase1
python workspace/phase1/reference.py
```

然后确认：

- `task.json` 是否存在；
- 数据文件名是否正确；
- `reference.py` 是否可以独立运行；
- `agent.py` 是否符合课程接口；
- API 配置是否正确；
- 课程服务是否启动。

阶段二则同理

---

### Q6：Agent 能运行，但是答案错误怎么办？

这通常不是“环境安装问题”，而是数据分析逻辑问题。

按顺序检查：

```text
1. Task 是否理解正确
2. 字段是否选择正确
3. 数据类型是否正确
4. 过滤条件是否完整
5. 分组 / 聚合是否正确
6. 最终输出类型和格式是否正确
```

---

### Q7：reference.py 和 Agent 的答案不同，应该相信谁？

先检查 `reference.py` 本身是否真正符合 Task 定义。

标准答案程序必须满足：

```text
Task 定义正确
      +
Data 支持
      +
reference.py 逻辑正确
      ↓
唯一 Ground Truth
```

如果 reference.py 本身错误，应先修复标准答案程序，而不是为了“通过测试”去让 Agent 模仿错误答案。

# 附页A｜正式评测：精选测试集 + 攻防对抗

> **两种模式同时计入最终成绩**：精选测试集考察 Agent 的综合解题能力；攻防对抗考察 Agent 进攻表现与 Task 防守能力。

## ① 提交什么：最终参评成果

| 成果                        | 正式评测使用规则                                             |
| --------------------------- | ------------------------------------------------------------ |
| **Agent v2（矛）**          | **唯一**参加最终智能体评测；Agent v1 仅用于过程测试与迭代分析。 |
| **Task v1 + Task v2（盾）** | 两道题**分别审核**，合格的题目都有机会参与评测，最多 2 道。  |

## ② 什么有资格参评：规范与质量审核

Task 须题意明确、没有歧义、参考程序与标准答案正确，且学生自己的 Agent 能成功求解；应针对课程规定的 Failure Mode 设计。Agent 也须通过运行与提交规范审核。**超时、资源超限和运行时错误不能作为预期 Failure Mode 的有效证明。** 未通过审核的成果不具备对应参评资格，因此每名学生实际可能是 **0～1 个矛、0～2 个盾**。

## ③ 怎么评测：两种模式同时进行

| 模式一：精选测试集评测                                       | 模式二：攻防对抗评测（Elo Rating）                           |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 从有效 Task 中按失败模式覆盖、原创性、区分度等筛选优质题目；全部合格 **Agent v2** 统一解题。 | **Agent v2 为矛**，挑战其他同学的有效 Task；**Task v1/v2 为盾**，接受其他 Agent 挑战。 |
| Agent 解对的精选题越多，表现越好；**题目入选精选测试集可获得额外加分**。 | 使用 **Elo Rating** 分别形成进攻与防守排名，并据此计分。     |

## ④ 如何计分：两种模式均影响最终成绩

精选测试集成绩体现 Agent 解题能力及入选任务贡献；攻防对抗成绩体现 Agent 进攻与 Task 防守排名。**具体成绩权重、Elo 配对数量、排名换分规则以后续正式评分细则为准**，此处不预设数值。

**必须记住的 4 条规则**：① 两轮 Task 分别审核、都可能参评；② 最终只评 Agent v2；③ Task 必须自己 Agent 能解；④ 程序崩溃、超时及资源超限不算规定失败模式的有效证明。

**模型说明**：正式评测计划采用 DeepSeek Flash（暂定 `deepseek-v4.1-flash`）及可能的其他未公开基座模型。Agent 应具备跨模型适应能力，不能针对单一模型结果硬编码。

---

# 附页B｜最终成绩：由 4 项评测结果综合计算

> **成绩同时看出题质量与解题能力**：题目质量、精选测试集解题表现、Elo 进攻排名、Elo 防守排名四项结果共同决定最终成绩。

| 成绩组成                        | 评什么                                           | 如何得到分数                                               |
| ------------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| **① 题目质量得分（\(S_Q\)）**   | Task v1 / Task v2 的有效性、原创性与挑战性       | 通过任务质量审核；高质量题目入选精选测试集可获得额外加分。 |
| **② 测试集解题得分（\(S_T\)）** | Agent v2 对精选测试集的综合解题能力              | Agent v2 统一解题，正确解决的有效题目越多，表现越好。      |
| **③ Elo 进攻得分（\(S_A\)）**   | Agent v2 作为“矛”，挑战其他同学的有效 Task       | 根据攻防结果计算 Elo 进攻排名，再按公布的规则转换成分数。  |
| **④ Elo 防守得分（\(S_D\)）**   | Task v1 / v2 作为“盾”，接受其他同学 Agent 的挑战 | 根据攻防结果计算 Elo 防守排名，再按公布的规则转换成分数。  |

## 最终成绩计算关系（建议表达，非已确定公式）

\最终成绩计算关系

同时保留了加权成绩关系：

$$
S_{\mathrm{final}}=w_QS_Q+w_TS_T+w_AS_A+w_DS_D
$$

同时保留了加权成绩关系：**W为对应权重。**

$$
S_Q为题目质量得分，S_T为精选测试集解题得分,S_T为精选测试集解题得分,S_A为 Elo 进攻得分,S_D为 Elo 防守得分。
$$

**特别说明：** 文档明确将此公式标记为建议表达，而非已经确定的正式评分公式。四项权重、精选题入选加分和 Elo 排名换分规则均留待课程组正式公布。

**重要说明**：这是用于说明成绩构成的**建议加权表达式**，不是已经公布的正式计分公式。四项权重、题目入选加分标准、无效成果处理方式、Elo 对抗数量和排名换分方法，均以课程组后续发布的正式评分细则为准。

**课堂强调**：① Task v1/v2 与 Agent v2 评价对象不同；② Elo 进攻与 Elo 防守是两套独立排名；③ 只提高 Agent 答题正确率，不等于一定获得最高总成绩。
