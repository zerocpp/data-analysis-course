## 一、课程概览：你要完成什么？

本课程采用 **“Task 为矛、Agent 为盾”** 的项目式学习方式：

- **Task（矛）**：设计一道明确、可执行、可验证的数据分析题，挑战其他同学的 Agent。
- **Agent（盾）**：基于大语言模型开发通用数据分析程序，尽可能正确地完成陌生 Task。
- **Reference（标准答案）**：为你设计的 Task 提供独立、确定、可复现的答案计算程序。

### 两个阶段的任务

| 阶段 | 你需要做的事 | 核心交付物 |
|---|---|---|
| **Phase 1：初始设计** | 设计 Task v1、准备 CSV、实现 `reference.py`、开发 Agent v1、本地测试、构建并验证提交包 | Task v1 + Agent v1 |
| **Phase 2：匿名挑战与优化** | 运行分配的约 10 道匿名题，分析结果并评审，形成 Task v2、Agent v2，撰写报告 | Task v2 + Agent v2 + `review-comments.json` + 实验报告 |

**完成标准**：文件与身份信息正确、参考程序能算出确定答案、Agent 能按照模板运行、正式 ZIP 已经本地验证通过。Task/Agent 是否优化到更高水平，取决于真实测试结果与设计质量。

### 推荐学习路线

```text
获取模型 API → 准备 WSL2/Ubuntu → 安装 Docker → 启动 DataChallenging
       ↓
Phase 1：task + csv + Reference + Agent → 运行 → 打包 → 校验
       ↓
Phase 2：接收匿名题 → 测试与评审 → 优化 Task/Agent → 报告 → 打包校验
```

# 正式评测：精选测试集 + 攻防对抗

> **两种模式同时计入最终成绩**：精选测试集考察 Agent 的综合解题能力；攻防对抗考察 Agent 进攻表现与 Task 防守能力。

## ① 提交什么：最终参评成果

| 成果                        | 正式评测使用规则                                             |
| --------------------------- | ------------------------------------------------------------ |
| **Agent v2（矛）**          | **唯一**参加最终智能体评测；Agent v1 仅用于过程测试与迭代分析。 |
| **Task v1 + Task v2（盾）** | 两道题**分别审核**，合格的题目都有机会参与评测，最多 2 道。  |

## ② 什么有资格参评：规范与质量审核

Task 须题意明确、没有歧义、参考程序与标准答案正确，且学生自己的 Agent 能成功求解；应针对课程规定的 Failure Mode 设计。Agent 也须通过运行与提交规范审核。**超时、资源超限和运行时错误不能作为预期 Failure Mode 的有效证明。** 未通过审核的成果不具备对应参评资格，因此每名学生实际可能是 **0～1 个矛、0～2 个盾**。

## ③ 怎么评测：两种模式同时进行

| 模式一：精选测试集评测                                       | 模式二：攻防对抗评测（Elo Rating）                           |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 从有效 Task 中按失败模式覆盖、原创性、区分度等筛选优质题目；全部合格 **Agent v2** 统一解题。 | **Agent v2 为矛**，挑战其他同学的有效 Task；**Task v1/v2 为盾**，接受其他 Agent 挑战。 |
| Agent 解对的精选题越多，表现越好；**题目入选精选测试集可获得额外加分**。 | 使用 **Elo Rating** 分别形成进攻与防守排名，并据此计分。     |

## ④ 如何计分：两种模式均影响最终成绩

精选测试集成绩体现 Agent 解题能力及入选任务贡献；攻防对抗成绩体现 Agent 进攻与 Task 防守排名。**具体成绩权重、Elo 配对数量、排名换分规则以后续正式评分细则为准**，此处不预设数值。

**必须记住的 4 条规则**：① 两轮 Task 分别审核、都可能参评；② 最终只评 Agent v2；③ Task 必须自己 Agent 能解；④ 程序崩溃、超时及资源超限不算规定失败模式的有效证明。

**模型说明**：正式评测计划采用 DeepSeek Flash（暂定 `deepseek-v4.1-flash`）及可能的其他未公开基座模型。Agent 应具备跨模型适应能力，不能针对单一模型结果硬编码。

**一句话记忆：精选测试集看 Agent 能解多少题；攻防对抗看 Agent 能攻、Task 能守。**

## 三、安装与启动本地环境

### 3.1 Windows 安装 WSL2 + Ubuntu 22.04 LTS

在 **Windows PowerShell（管理员）**中运行：

```powershell
wsl --update
wsl --install -d Ubuntu-22.04
wsl -l -v
```

首次进入 Ubuntu 后设置自己的 Linux 用户及密码。如果安装阶段提示重启，请先重启 Windows。若 `wsl -l -v` 显示 Ubuntu 是 WSL 1，可在 PowerShell 中执行：

```powershell
wsl --set-version Ubuntu-22.04 2
```

在 Ubuntu 中确认版本，并启用 `systemd`（若已经显示 `systemd`，无需修改）：

```bash
cat /etc/os-release
ps -p 1 -o comm=
```

如需启用 `systemd`，在 Ubuntu 执行：

```bash
sudo mkdir -p /etc
printf '[boot]\nsystemd=true\n' | sudo tee /etc/wsl.conf
```

再回到 **Windows PowerShell** 执行 `wsl --shutdown`，重新进入 Ubuntu 并检查 `ps -p 1 -o comm=`。

> 源手册还包含将 WSL 默认用户设为 `root` 的部署方式。是否以 root 运行，应按教师发放的镜像和目录权限要求执行；一般不必为了安装 WSL 而强制改为 root 默认登录。

### 3.2 Ubuntu 安装 Docker Engine 与 Compose

以下为原手册的 **Docker 官方仓库方式（Ubuntu 22.04）**，在 Ubuntu 中执行：

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF2
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF2

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

**Notes： Docker 官方仓库的 `docker-ce` 与 Ubuntu 仓库的 `docker.io` 两套安装方法混用。**

检查：

```bash
docker version
docker compose version
docker ps
```

若普通用户无 Docker 权限，联系助教或按课程环境说明处理；不要通过随意修改系统目录权限解决。

## 五、Phase 1：设计 Task 和 Agent

### 5.1 设计一道 Task

一个合格 Task = **任务描述 + CSV 数据 + 可执行参考答案**。

源手册使用的 `task.json` 关键字段示例：

```json
{
  "description": "统计某年度指定地区和渠道的销售总额",
  "task_statement": "筛选 year 为 2023、region 为 NE、channel 为 online 的记录，对 amount 求和，返回数值答案。",
  "hypothesized_failure_mode": "FM_AGGREGATION",
  "answer": 225
}
```

**题目写作要点**：说清数据范围、过滤条件、计算口径与输出格式；允许设计缺失值、重复记录、缩写、边界等有意义的挑战，但不允许靠损坏 CSV 或让程序无法执行制造失败。

### 5.2 准备 `data.csv`

示例：

```csv
year,region,channel,amount
2023,NE,online,120
2023,NE,online,80
2023,NE,online,25
2023,SW,online,50
2022,NE,online,40
2023,NE,offline,60
```

这个示例对应的求和结果为 `225`。检查 CSV：

```bash
python - <<'PY'
import pandas as pd
x = pd.read_csv('phase1/data.csv')
print(x.head())
print(x.dtypes)
print(x.shape)
PY
```

运行位置必须保证 `phase1/data.csv` 存在；如果已进入 `phase1` 目录，则改为 `pd.read_csv('data.csv')`。数据规模、依赖范围等遵守当前课程的限制，不以个人机器配置为准。

### 5.3 编写 `reference.py`

参考程序直接计算标准答案，必须稳定、可复现：

```python
# 以下仅展示计算逻辑；函数签名和输出协议以官方模板为准
result = df.loc[
    (df['year'] == 2023) &
    (df['region'] == 'NE') &
    (df['channel'] == 'online'),
    'amount'
].sum()
```

参考程序不应调用 LLM、依赖随机数、私有文件或网络。按模板完成程序后执行：

```bash
bin/datac reference run --phase phase1
```

确认参考程序状态为 `PASS`，并检查结果与题目要求一致。

### 5.4 开发 `agent.py`

Agent 不应只解决自己的题，而应能解决其他人设计的不同 CSV 分析任务。推荐流程：

```text
读取任务 → 探索 CSV 字段/值/缺失情况 → 理解问题
        → 规划步骤 → 数据计算 → 检查结果 → 返回答案
```

可以通过课程指定大模型 API 实现需求理解、生成程序或分步规划。必须遵守课程模板的 `agent.py` 接口、计算资源限制与答案输出协议，不要将参考答案硬编码进 Agent。

### 5.5 本地运行与 Phase 1 提交

在包含 `bin/datac` 的课程目录中运行：

```bash
# 分别验证参考答案与 Agent
bin/datac reference run --phase phase1
bin/datac run --phase phase1

# 查看当前 CLI 的提交参数
bin/datac submission build --help
bin/datac submission validate --help
```

源手册另有基于 `--workspace` 的旧式调用，**实际应以当前 `--help` 显示的参数为准**。若当前 CLI 支持以下参数，可按照教师公布的提交方式构建：

```bash
bin/datac submission build \
  --input /workspace/phase1 \
  --student-id 你的学号 \
  --phase P1
```

使用构建命令**实际打印出来的 ZIP 路径**进行验证：

```bash
ZIP_PATH="/workspace/phase1/submission/实际生成的文件.zip"  # 按实际输出替换
bin/datac submission validate \
  --input "$ZIP_PATH" \
  --phase P1
```

只有最终要上传的 ZIP 检查通过才完成本阶段提交。不要手动修改或重新压缩已构建的 ZIP。

## 六、Phase 2：匿名任务挑战与最终优化

### 6.1 导入 10 道匿名任务

收到教师发放的匿名任务压缩包后，按实际包名执行：

```bash
ANON_PKG="/workspace/实际发放的匿名包.tar.gz"  # 请替换为真实包名
bin/datac exposure import \
  --package "$ANON_PKG" \
  --workspace /workspace

bin/datac exposure status --workspace /workspace
```

源手册给出的检查目标：导入后 `tasks=10/10`、`done=0`。匿名任务通常以 `ATxxx` 标识，不代表题目作者身份。

### 6.2 使用 Agent 测试陌生 Task

```bash
bin/datac exposure run --workspace /workspace
bin/datac exposure status --workspace /workspace
```

正常完成后检查 `done=10`（实际以平台结果为准）。记录 Agent 正确、答案错误或执行失败的情况，分析任务歧义、字段识别、筛选逻辑、缺失值、数据类型、规划过程等原因。

**匿名评测只应使用平台批准的可见内容**。参考程序与标准答案应由教师端私有保存；如发现匿名包包含 `reference.py` 或可直接读出 `answer` 的私有元数据，不要据此调试 Agent，应反馈助教排查匿名化问题。

### 6.3 填写 `review-comments.json`

对收到的每道匿名 Task 给出 **1–5 分的整数评分**和**非空具体评语**。以下是结构示例：

```json
{
  "AT003": {
    "score": 4,
    "comments": "计算目标清楚，但边界条件还可补充。"
  },
  "AT013": {
    "score": 5,
    "comments": "数据设计合理，可以有效考察分组聚合。"
  }
}
```

真正提交时应覆盖所有分配到的匿名 Task ID（一般为 10 个），每个 ID 恰好一条。部分课程模板可能还包含 `task_id` 字段，**保留原模板的必填字段，不要仅凭本示例删字段**。

### 6.4 完成 Task v2 和 Agent v2

在 `phase2/` 工作区完成最终版本：

- **Task v2**：可根据分析重新设计，也可以与 v1 相同。
- **Agent v2**：针对匿名测试中的失败原因改进，也可以保持 v1 不变。
- **无需新增 `task_v2.json` 或 `agent_v2.py`**：修改对应阶段工作区的标准文件即可。
- 无论是否修改，都应在实验报告中说明设计选择及原因。

完成后执行：

```bash
bin/datac reference run --phase phase2
bin/datac run --phase phase2
bin/datac submission build --help
```

源手册中 Phase 2 的 `submission build` 示例与 ZIP 文件名存在前后不一致（有的示例未写 `--phase`，却显示 `bigdata_p1_...zip`）。因此，**正式以当前 CLI 的 Phase 2 帮助信息、教师发布要求和实际构建输出为准**，不要直接套用 Phase 1 的 ZIP 文件名。构建后仍须对实际 ZIP 执行 `submission validate`。



# 最终成绩：由 4 项评测结果综合计算

> **成绩同时看出题质量与解题能力**：题目质量、精选测试集解题表现、Elo 进攻排名、Elo 防守排名四项结果共同决定最终成绩。

| 成绩组成             | 评什么                                           | 如何得到分数                                               |
| -------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| **① 题目质量得分**   | Task v1 / Task v2 的有效性、原创性与挑战性       | 通过任务质量审核；高质量题目入选精选测试集可获得额外加分。 |
| **② 测试集解题得分** | Agent v2 对精选测试集的综合解题能力              | Agent v2 统一解题，正确解决的有效题目越多，表现越好。      |
| **③ Elo 进攻得分**   | Agent v2 作为“矛”，挑战其他同学的有效 Task       | 根据攻防结果计算 Elo 进攻排名，再按公布的规则转换成分数。  |
| **④ Elo 防守得分**   | Task v1 / v2 作为“盾”，接受其他同学 Agent 的挑战 | 根据攻防结果计算 Elo 防守排名，再按公布的规则转换成分数。  |

## 最终成绩计算关系

同时保留了加权成绩关系：

$$
S_{\mathrm{final}}=w_QS_Q+w_TS_T+w_AS_A+w_DS_D
$$

同时保留了加权成绩关系：**W为对应权重。**

$$
S_Q为题目质量得分，S_T为精选测试集解题得分,S_T为精选测试集解题得分,S_A为 Elo 进攻得分,S_D为 Elo 防守得分。
$$

**特别说明：** 文档明确将此公式标记为建议表达，而非已经确定的正式评分公式。四项权重、精选题入选加分和 Elo 排名换分规则均留待课程组正式公布。

**重要说明**：这是用于说明成绩构成的**建议加权表达式**，不是已经公布的正式计分公式。四项权重、题目入选加分标准、无效成果处理方式、Elo 对抗数量和排名换分方法，均以课程组后续发布的正式评分细则为准。

**课堂强调**：① Task v1/v2 与 Agent v2 评价对象不同；② Elo 进攻与 Elo 防守是两套独立排名；③ 只提高 Agent 答题正确率，不等于一定获得最高总成绩。

| 章节 | 核心内容 |

## 七、认识运行结果与常见失败模式

### 7.1 三类常见运行结果

| 结果 | 解释 | 首先检查 |
|---|---|---|
| 正确完成 | Agent 结果符合标准答案 | 保留有效测试记录 |
| 答案错误 | 程序运行完成，但数据分析结果不正确 | 任务理解、字段、筛选、聚合、精度、输出类型 |
| 运行失败 | Agent 或依赖服务未完成运行 | Python 异常、文件路径、模型 API、CLI 接口、Docker 状态 |

**Reference 结果不是天然正确**：若发现参考答案与题目描述不一致，先修正参考程序和 Task，不能让 Agent 模仿错误答案。

### 7.2 14 类 Failure Mode 速查

| 编号 | 含义 | 编号 | 含义 |
|---|---|---|---|
| `FM_REQUIREMENT` | 需求理解 | `FM_SCHEMA` | 字段/Schema 理解 |
| `FM_DATA_TYPE` | 数据类型 | `FM_FILTER_SORT` | 筛选/排序 |
| `FM_JOIN` | 关联/Join | `FM_AGGREGATION` | 分组/聚合 |
| `FM_TIME_TIMEZONE` | 时间/时区 | `FM_MISSING_VALUE` | 缺失值 |
| `FM_OUTLIER_BOUNDARY` | 异常值/边界 | `FM_DUPLICATE_RECORD_HANDLING` | 重复记录 |
| `FM_PLANNING_DECOMPOSITION` | 规划分解 | `FM_VERIFICATION` | 结果验证 |
| `FM_NUMERICAL_PRECISION_ROUNDING` | 数值精度/舍入 | `FM_PROMPT_INJECTION` | 不可信数据中的指令干扰 |

Task 的 `hypothesized_failure_mode` 应填写课程定义的完整编号。

设计失败模式是为了检验智能体分析能力，**不是允许通过恶意指令、非法文件或破坏运行环境作弊**。

## 八、常见问题（FAQ）

| 问题 | 排查方式 |
|---|---|
| WSL 启动失败 | 在 PowerShell 执行 `wsl -l -v`，检查是否为 WSL2，按提示重启 |
| Docker 无法运行 | 在 Ubuntu 执行 `sudo systemctl start docker`，检查 `docker ` 与 `docker compose`版本 |
| d`bin/datac` 找不到 | 确认位于实际包含 `bin/datac` 的课程目录，再运行 `bin/datac --help` |
| Agent 调用模型失败 | 检查 `.env` 变量、Base URL、模型权限、网络及剩余额度 |
| `reference run` 失败 | 核对 `task.json`、`data.csv`、`reference.py` 及对应 `--phase` |
| Agent 能运行但答案错误 | 检查任务理解、数据类型、筛选条件、聚合计算和最终输出格式 |
| 无法构建提交包 | 检查 `metadata.json` 中学号与 ID、必填文件、JSON 格式、`review-comments.json` |
| 提交 ZIP 检查失败 | 对构建命令产生的**同一个 ZIP**执行 `submission validate`，不要手工二次压缩 |
| 不知道用什么参数 | 运行 `bin/datac submission build --help`，并核对助教发布的 Phase 2 要求 |
