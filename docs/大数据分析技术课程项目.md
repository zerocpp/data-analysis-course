## 明确失败模式

FM（Failure Mode）用于说明设计的 Task 主要希望考查 Agent 的哪一种错误类型。

例如，一道题要求先筛选数据再计算平均值，如果希望重点考查 Agent 是否能够正确理解聚合计算规则，就可以选择 `FM_AGGREGATION`。

需要注意：**FM 是在出题时候预先设定的目标失败模式，不代表 Agent 实际运行时一定会出现这种错误。**

必须根据自己设计的 Task，选择最匹配的一种失败模式，并按照系统规定的格式提交。失败模式必须填写。

**1. FM 必须从系统规定的 14 种类型中选择**

目前系统支持以下 14 种标准失败模式：

| 编号 | 失败模式             | 必须填写的 Failure Mode Key       |
| ---- | -------------------- | --------------------------------- |
| FM01 | 需求理解偏差         | `FM_REQUIREMENT`                  |
| FM02 | Schema 理解错误      | `FM_SCHEMA`                       |
| FM03 | 数据类型处理错误     | `FM_DATA_TYPE`                    |
| FM04 | 筛选或排序错误       | `FM_FILTER_SORT`                  |
| FM05 | Join / 关联错误      | `FM_JOIN`                         |
| FM06 | 聚合口径错误         | `FM_AGGREGATION`                  |
| FM07 | 时间与时区错误       | `FM_TIME_TIMEZONE`                |
| FM08 | 缺失值处理错误       | `FM_MISSING_VALUE`                |
| FM09 | 异常值或边界处理错误 | `FM_OUTLIER_BOUNDARY`             |
| FM10 | 重复记录处理错误     | `FM_DUPLICATE_RECORD_HANDLING`    |
| FM11 | 规划与分解错误       | `FM_PLANNING_DECOMPOSITION`       |
| FM12 | 验证不足             | `FM_VERIFICATION`                 |
| FM13 | 数值精度与舍入错误   | `FM_NUMERICAL_PRECISION_ROUNDING` |
| FM14 | 提示注入或不可信数据 | `FM_PROMPT_INJECTION`             |

特别注意：

- 每道 Task 必须选择一个主要失败模式。
- 必须填写第三列中的完整英文 Key。
- 第一列的 FM01、FM02 等编号仅用于展示和分类，不能作为提交值。
- 不允许自行创建新的失败模式。
- 不允许使用数字编号、简写或小写形式代替标准 Key。

例如：

正确：

```
FM_AGGREGATION
```

错误：

```
FM06_AGGREGATION
FM_06_AGGREGATION
fm_aggregation
FM_BOGUS
```

强调正式提交校验只接受标准 Key。

**2. FM 应该填写在哪里？**

FM 必须填写在 `metadata.json` 的 `hypothesized_failure_mode` 字段中。

例如：

```json
{
  "hypothesized_failure_mode": "FM_AGGREGATION"
}
```

以上仅展示 FM 字段的正确写法，不代表完整的 `metadata.json` 只需要这一个字段。其他字段仍须按照课程提供的模板保留。

**3. 应该如何选择合适的 FM？**

建议先确定自己设计的 Task 主要考查 Agent 的什么能力，再选择对应的失败模式。

下面给出一些简单示例：

| 失败模式             | 示例任务或潜在错误                             |
| -------------------- | ---------------------------------------------- |
| 需求理解偏差         | 题目要求统计用户数量，Agent 却统计了记录数量   |
| Schema 理解错误      | 将 `amount` 字段误认为数量，而不是金额         |
| 数据类型处理错误     | 把数值字符串当作普通文本处理                   |
| 筛选或排序错误       | 题目要求先取最新记录，Agent 却先筛选状态       |
| Join / 关联错误      | 按错误的关联字段连接数据                       |
| 聚合口径错误         | 应按用户分组求和，却直接计算全表总和           |
| 时间与时区错误       | 未按题目要求统一时间或处理时区                 |
| 缺失值处理错误       | 题目要求缺失值按 0 计算，Agent 却直接跳过      |
| 异常值或边界处理错误 | 将金额等于阈值的记录错误排除                   |
| 重复记录处理错误     | 未按题目要求去除重复记录                       |
| 规划与分解错误       | 多步骤计算时遗漏其中一个必要步骤               |
| 验证不足             | 得到中间结果后未检查是否符合最终统计口径       |
| 数值精度与舍入错误   | 应在最终结果保留两位小数，却提前对中间结果舍入 |
| 提示注入或不可信数据 | 将 CSV 中不可信的文本内容误当作需要执行的指令  |

以上是帮助理解不同 FM 的示例，不代表选择该标签后，Agent 就一定会出现对应错误。

**4. 一道 Task 涉及多个 FM，应该怎么选？**

一道数据分析题可能同时涉及筛选、排序、重复记录和聚合。

例如：

题目要求先选取每个用户的最新记录，再筛选状态为 ACTIVE 的用户，最后统计符合条件的用户数量。

这道题既涉及排序，也涉及筛选和聚合。

但是，如果最希望考查的是 Agent 是否能够正确执行“先选择最新记录，再判断状态”的操作顺序，那么应优先选择：

```
FM_FILTER_SORT
```

而不是因为最终使用了计数操作，就选择 `FM_AGGREGATION`。

建议按照以下原则选择：

- 首先明确题目最希望考查的错误类型。
- 再判断哪一种 FM 最能代表这道题的主要难点。
- 如果涉及多种处理操作，优先选择最关键、最具有区分性的错误类型。
- 不要为了选择某种 FM，故意设计不合理或存在歧义的题目。

**原则：FM 应当反映 Task 的主要考查目标，而不是简单列举 Task 使用了哪些数据处理操作。**

**5. FM 必须与 Task 的实际设计相匹配**

填写某个 FM 后，题目本身应当具有考查这种能力的合理依据。

例如，选择 `FM_MISSING_VALUE`，但 `data.csv` 中完全没有缺失值，题目也不涉及缺失值处理，那么这个失败模式就缺乏相应的设计依据。

同样，选择 `FM_TIME_TIMEZONE`，但题目既不涉及时间字段，也不涉及任何时间计算，那么这一分类通常也不合适。

需要特别区分：

**可以主动设计容易让 Agent 出错的数据和处理规则，但不能故意把题目写错。**

例如，允许设置：

- 先筛选和先排序会得到不同结果的数据。
- 包含缺失值和异常值的数据。
- 包含重复记录或临界值的数据。
- 需要多步骤推理才能得到正确结果的任务。

但必须保证：

- 题目要求明确。
- 数据能够支持正确计算。
- `reference.py` 按照题目要求实现。
- `answer` 是正确且可独立复核的标准答案。

**6. FM 不会提前告诉被测 Agent**

FM 属于出题者的设计信息，不是 Agent 解题所必需的公开信息。

在正式匿名评测中，系统会从 Task 的公开内容中移除 FM 字段，避免提前向被测 Agent 暴露题目的预设考查方向。

因此：

- 不要在 `task.json` 中额外填写 FM 字段。
- 不要通过嵌套 JSON 或其他变形字段隐藏 FM。
- 不要在公开题目中直接泄露标准答案或私有设计信息。
- 不要尝试通过额外文件向被测 Agent 传递 FM。

Task 的匿名版本应当只向 Agent 提供允许公开的任务信息和数据。

FM 则由教师端保留，用于后续实验统计与分析。

如果匿名 Task 中泄露了 FM 字段，系统可能报出 `EXPOSURE_LEAK`。

**7. 预设 FM 不等于实际发生的 FM**

填写的 `hypothesized_failure_mode` 只是对任务难点的预先判断。

例如，为一道题选择：

```
FM_FILTER_SORT
```

正式测试后，可能出现以下情况：

- Agent 正确完成任务，没有发生错误。
- Agent 正常返回错误答案，经过分析确认属于筛选顺序错误。
- Agent 正常返回错误答案，但实际原因是需求理解错误。
- Agent 因模型接口故障或资源超限而没有正常完成任务。

这些情况不能全部视为发生了 `FM_FILTER_SORT`。

系统会先区分 Agent 是否正常完成执行：

| 运行结果           | 含义                                         | 是否属于 FM 分析对象       |
| ------------------ | -------------------------------------------- | -------------------------- |
| `completed`        | Agent 正常返回正确答案                       | 不作为失败样本             |
| `analysis_failure` | Agent 正常返回答案，但答案不正确             | 是，需要进一步分析实际错误 |
| `internal_error`   | API、Token、资源或运行环境等原因导致执行异常 | 否，不计入 FM 统计         |

特别注意：

**Agent 返回错误答案，并不能直接证明发生了预设的 FM。**

需要进一步检查 Agent 的解题过程、计算结果和可验证的错误证据，才能判断实际失败类型。

助教端后续可以对比“任务包预设的 FM”和“Agent 实际发生的 FM”，分析不同 Task 的错误诱发效果。

**8. Phase 1 与 Phase 2 的填写要求**

Phase 1 和 Phase 2 的 `metadata.json` 均须包含合法的 `hypothesized_failure_mode`。

如果 Phase 2 修改了题目或数据，应重新检查当前 FM 是否仍然与任务设计一致。

不能因为 Phase 1 已经填写过 FM，就忽略 Phase 2 的对应检查。

此外，FM 只保留在外层的 `metadata.json` 中。

正式生成的 `Tasks_<学号>` 包内只包含：

```text
Tasks_<学号>/
├── task.json
├── data.csv
└── reference.py
```

不包含 `metadata.json`，也不在内部 `task.json` 中额外加入 FM 字段。

**9. 提交前必须自查**

| 检查项目          | 要求                                          |
| ----------------- | --------------------------------------------- |
| FM 是否填写       | 必须填写，不允许缺失                          |
| 填写位置          | 仅在 `metadata.json` 中                       |
| 字段名称          | `hypothesized_failure_mode`                   |
| Key 格式          | 必须使用 14 种标准 Key 之一                   |
| 数字编号          | 不允许使用 FM01、FM06 等编号形式作为提交值    |
| 自定义类别        | 不允许自行增加                                |
| 主要失败模式      | 每道 Task 选择一个最匹配的类别                |
| 与题目一致        | FM 应能反映 Task 的主要考查目标               |
| 公开内容          | 不得在 `task.json` 或匿名 Task 中泄露 FM 字段 |
| Phase 1 / Phase 2 | 两阶段均须正确填写                            |
| 实际失败判断      | 不能直接把预设 FM 当作已验证的失败原因        |

**最后强调：FM 是设计 Task 时选择的目标错误类型，不是提前确定的实验结论。**

需要围绕某一种具有代表性的失败模式设计题目，保证数据、计算规则、Reference 和标准答案正确，再通过实际 Agent 测试检验这道题能否诱发相应错误。

题目可以有针对性，但不能通过模糊规则、错误数据或错误标准答案来制造失败。

### 2.5.3 规定Task，Agent

#### <a id="task-analysis"></a>

#### Task：一道完整的数据分析题 ⭐️⭐️⭐️

Task 是一套完整、可执行、可验证的任务材料。

**每道 Task 必须包含以下三个文件task.json（题面） data.csv（数据表）和 reference.py（参考代码） ：**

```
phase1/
└── 20250001/
    ├── task/
    │   ├── task.json
    │   ├── data.csv
    │   └── reference.py
    │
    ├── agent/
    │   └── agent.py
    │
    └── metadata.json
```

三个文件的作用分别是：

| 文件         | 作用                       | 要求                        |
| ------------ | -------------------------- | --------------------------- |
| task.json    | 说明题目要求及标准答案信息 | 题意完整、规则明确          |
| data.csv     | 提供题目所需的原始数据     | 数据真实、格式正确、可读取, |
| reference.py | 实现题目的标准求解过程     | 能够执行，得到正确答案      |

其中，`reference.py` 是这道题的标准求解程序。执行它所得到的结果，必须与 `task.json` 中的 `answer` 一致。

**简单来说：Task 是你设计的一道能够通过程序执行和验证的数据分析题，而不是一道只有文字描述的问答题，Task是包含了三个文件：task.json（题面） data.csv（数据表）和 reference.py（参考代码）。**



#### a) task.json 应该如何编写？

基本格式如下：

```
{
  "description": "一句话概括你的任务。",
  "task_statement": "完整说明数据、计算要求和最终输出格式。",
  "answer": 30
}
```

四个字段分别有明确要求。

**1. description：任务简介**

用一句话说明这道题要完成什么，不需要展开具体计算过程。

**2. task_statement：完整任务说明**

建议严格按照以下四个部分组织：

- 数据说明：有哪些数据文件、字段名称、字段含义和数据类型。
- 筛选或处理规则：具体需要筛选什么、如何排序、如何处理缺失值、重复值和异常数据等。
- 计算目标：需要进行什么统计、聚合、比较或计算。
- 输出要求：明确最终返回什么结果，结果的数据类型、格式和精度是什么。

特别注意：不能只写大致思路，必须把影响最终答案的规则说清楚。

例如，如果要求选择每个用户最新的一条记录，就必须明确日期相同时如何处理；如果要求计算平均值，就必须明确缺失值是否参与计算。

**3. answer：标准答案**

`answer` 必须来自实际执行 `reference.py` 的结果，而不是人工估算或直接填写一个预期数字。

提交前必须确认：

- reference.py 能够正常运行；
- reference.py 实际读取 data.csv；
- 输出结果符合 task_statement 的要求；
- 执行结果与 answer 完全一致。



#### b) data.csv 应该如何编写？

`data.csv` 是 Task 的数据文件，必须包含完成 `task_statement` 所需的数据。

自行设计数据内容，包括字段、记录数量、数值范围和异常情况，但必须满足系统规定的文件限制，并确保数据能够支持题目要求的计算。

**1. 文件格式与大小限制**

系统对 `data.csv` 有以下硬性要求：

| 检查项目 | 具体要求                                        |
| -------- | ----------------------------------------------- |
| 文件名   | 必须命名为 `data.csv`                           |
| 文件大小 | 不超过 1,048,576 字节（1 MB）                   |
| 数据行数 | 严格少于 10,000 行，最多 9,999 行               |
| 数据列数 | 不超过 100 列                                   |
| 文件编码 | 必须使用 UTF-8 编码                             |
| 文件格式 | 必须能够通过 Python 的 `pd.read_csv()` 正常读取 |

特别注意：

- **行数不包含表头。** 例如，第一行是字段名，后面有 9,999 行数据，符合行数限制。
- **文件大小按实际字节计算。** 即使行数和列数没有超限，文件超过 1,048,576 字节也会校验失败。
- **必须保存为 UTF-8 编码。** 使用 GBK 等其他编码可能导致文件读取失败。
- 以上限制是系统固定规则，不能通过修改 `.env` 配置绕过。

**2. 数据字段与题目保持一致**

`data.csv` 中的字段名称、字段含义和数据内容必须与 `task_statement` 一致。

例如，题目要求根据用户编号、日期和状态统计最新状态为 ACTIVE 的用户数量，那么数据表就应提供完成这一计算所需的字段。

示例：

```csv
user_id,date,status
U01,2026-01-01,ACTIVE
U01,2026-01-03,INACTIVE
U02,2026-01-02,ACTIVE
U03,2026-01-04,ACTIVE
```

对应的题目可以要求：

对每个用户，先按照日期选择最新的一条记录，再统计最新状态为 ACTIVE 的用户数量，最终输出一个整数。

该示例的正确答案为 `2`。

数据设计时应注意：

- 字段名称应清楚，建议使用明确的表头，避免重复字段名。
- 字段含义和数据类型应与题干描述一致。
- 题目需要用到的字段和数据必须实际存在。
- 不得要求 Agent 读取未提供的其他数据文件。
- 不得依赖作者本地文件、私人数据库或外部网络数据才能完成计算。

**3. 缺失值、重复值与异常数据必须有明确规则**

允许在 `data.csv` 中设置缺失值、重复记录、非法数值、日期异常和其他具有挑战性的情况。

这些数据可以用来考查 Agent 的数据处理能力，但不能让题目变得含糊不清。

例如：

```csv
user_id,amount
U01,100
U02,
U03,abc
U04,200
```

其中，`U02` 的金额缺失，`U03` 的金额无法正常转换为数字。

如果题目要求计算金额总和，就必须在 `task_statement` 中说明：

- 缺失金额如何处理；
- 非法数值如何处理；
- 是否需要排除某些记录；
- 最终使用什么数值精度。

同样，如果数据包含重复记录、相同日期或排序并列等情况，也必须说明对应的处理方式。

**原则：允许设置容易出错的数据，但必须给出明确的处理规则。**

不是要求每道题都包含所有异常情况，而是只要某种情况可能影响答案，就必须说明如何处理。

**4. 数据必须能够支持正确、可复现的计算**

`data.csv` 不能只是形式上满足文件要求，还必须与 `task.json` 和 `reference.py` 相互一致。

具体要求：

- `task_statement` 中规定的计算能够使用提交的数据完成。
- `reference.py` 必须实际读取 `data.csv`，按照题目要求计算。
- `task.json` 中的 `answer` 必须与正确执行参考程序的结果一致。
- 相同数据、题目和运行环境下，应该能够重复得到相同答案。
- 不得故意设计与题干矛盾的数据，或者通过错误数据制造不合理的标准答案。

特别注意：一道Task除了检查程序运行结果，还需要检查计算逻辑是否正确，必要时使用边界数据进行验证。

**5. Phase 1 与 Phase 2 的数据要求**

Phase 1 和 Phase 2 均须遵守上述文件限制。

如果 Phase 2 要求修改数据，应当直接修改对应的 `phase2/data.csv`，并重新执行 `reference.py`，核对 `task.json` 中的 `answer` 是否仍然正确。

不能只修改 `answer`，而不重新验证数据和参考程序之间的一致性。

**6. 提交前必须自查**

| 检查项目   | 要求                                   |
| ---------- | -------------------------------------- |
| 文件名称   | `data.csv`，不得自行更名               |
| 文件大小   | ≤ 1,048,576 B                          |
| 数据行数   | ≤ 9,999 行（不含表头）                 |
| 数据列数   | ≤ 100 列                               |
| 编码格式   | UTF-8                                  |
| 文件读取   | `pd.read_csv()` 能够正常读取           |
| 字段一致性 | 字段名称和含义与题干一致               |
| 数据完整性 | 所需计算不依赖其他未提供数据           |
| 特殊情况   | 影响答案的异常和边界情况有明确处理规则 |
| 结果正确性 | 数据、Reference 和标准答案相互一致     |

**最后强调：数据不能模糊；可以故意设置容易让 Agent 出错的情况，但不能故意制造错误标准答案。**

系统不仅检查 CSV 是否符合文件格式和大小要求，后续还会检查数据是否真正支持题目计算，以及参考程序和标准答案是否正确。

#### c) reference.py 应该如何编写？

`reference.py` 是 Task 的参考求解程序，用于根据 `data.csv` 中的数据，按照 `task_statement` 规定的规则计算标准答案。

可以自行设计计算逻辑，但必须遵守系统规定的代码格式、运行限制和答案一致性要求。

**1. 文件格式与代码限制**

系统对 `reference.py` 有以下硬性要求：

| 检查项目      | 具体要求                                                   |
| ------------- | ---------------------------------------------------------- |
| 文件名        | 必须命名为 `reference.py`                                  |
| 代码行数      | 严格少于 200 行，最多 199 行                               |
| Python 语法   | 必须能够通过 `ast.parse()` 语法检查                        |
| import 白名单 | 只允许导入 `pandas` 和 `decimal`                           |
| 相对导入      | 禁止使用                                                   |
| 文件读取      | 禁止使用 `open()` 和 pandas 的 `read_*()` 方法读取外部数据 |
| 文件写出      | 禁止使用 `to_csv()`、`to_excel()` 等方法写出数据           |
| 危险函数      | 禁止调用 `exec()`、`eval()`、`compile()`、`__import__()`   |
| 单次计算超时  | `reference(df)` 必须在 1 秒内完成执行                      |

特别注意：

- 不能导入 `numpy`、`os`、`json` 等白名单之外的模块。
- 可以使用 Python 允许的内置计算函数以及 pandas 提供的数据处理功能。
- 不允许读取其他 CSV、Excel、数据库或外部文件。
- 不允许通过网络请求、外部 API 或其他程序获取答案。
- 程序必须能够在课程统一运行环境中正常执行。

这些限制由系统自动检查，不是建议性的代码风格要求。

**2. 必须定义 reference(df) 函数**

系统要求 `reference.py` 中必须存在一个名为 `reference` 的可调用函数，而且参数名称必须是 `df`。

基本格式如下：

```python
def reference(df):
    # 按照题目要求处理数据
    result = int(df["amount"].sum())
    return result
```

其中：

- `df` 是系统从 `data.csv` 读取后传入的 pandas DataFrame。
- 函数内部按照题目要求进行筛选、排序、计算或聚合。
- 使用 `return` 返回最终计算结果。
- 返回值必须与 `task.json` 中的 `answer` 一致。

**特别注意：**

系统已经负责读取 `data.csv`，不需要在 `reference.py` 中再次读取文件。

因此，下面的写法不符合要求：

```python
import pandas as pd

def reference(df):
    data = pd.read_csv("data.csv")
    return int(data["amount"].sum())
```

正确做法是直接使用系统传入的 `df`：

```python
def reference(df):
    return int(df["amount"].sum())
```

函数名称和参数名称不能自行修改，也不能增加其他参数。例如，`solve(df)`、`reference(data)`、`reference(df, config)` 均不符合接口要求。

最终答案必须通过 `return` 返回，不能只使用 `print()` 输出。

**3. reference.py 必须真正实现题目要求**

参考程序不能只保证运行成功，还必须正确实现 `task_statement` 中规定的计算逻辑。

例如，题目要求：

对每个用户，先根据日期选择最新记录，再统计最新状态为 ACTIVE 的用户数量。

那么 `reference.py` 必须按照这个顺序处理数据。

不能先筛选 ACTIVE 状态，再选择最新记录，因为这两种计算方式可能得到不同结果。

编写时应注意：

- 筛选条件必须与题干一致。
- 排序、去重和分组顺序必须符合题目要求。
- 缺失值、异常值、重复记录和边界情况必须按照题干规定处理。
- 计算公式、数值精度及四舍五入规则必须与题干一致。
- 不得为了匹配预期答案而擅自改变计算规则。

**不能直接硬编码标准答案。**

例如：

```python
def reference(df):
    return 30
```

即使 `task.json` 中的 `answer` 也是 `30`，这种写法仍然不符合参考程序必须实际计算数据的要求。

正确做法是根据 `df` 中的数据完成计算。

**4. 运行时间与执行要求**

系统在执行 `reference(df)` 时设置了 **1 秒超时限制**。

因此，参考程序应尽量使用简单、明确、高效的数据处理方式。

建议：

- 优先使用 pandas 的筛选、排序、分组和聚合功能。
- 避免没有必要的多层循环和重复计算。
- 不要进行与题目无关的大规模计算。
- 不要使用无限循环、长时间等待或其他可能导致超时的操作。
- 不要依赖运行环境之外的文件、模块或服务。

如果函数执行超时或运行过程中出现异常，系统可能报出 `REFERENCE_ERROR`，导致提交失败。

此外，系统向函数传入的是数据副本，可以在函数内部进行必要的数据处理，但不能通过修改原始文件影响其他任务或评测结果。

**5. 计算结果必须与 answer 一致**

系统会真实执行 `reference.py`，再将计算结果与 `task.json` 中的 `answer` 比较。

例如：

`task.json`：

```json
{
  "description": "计算所有记录的金额总和。",
  "task_statement": "给定 data.csv，其中 amount 表示金额。计算全部记录的 amount 总和，最终返回一个整数。",
  "answer": 30
}
```

`reference.py`：

```python
def reference(df):
    result = int(df["amount"].sum())
    return result
```

假设 `data.csv` 中的金额分别为 `10` 和 `20`，则参考程序返回 `30`，与 `answer` 一致。

需要注意：

- 标准答案必须来自真实计算，而不能人工猜测或估算。
- 如果修改了数据或参考程序，必须重新运行并检查 `answer`。
- 系统对普通数值类型允许一定的数值归一化比较，例如整数 `30`、浮点数 `30.0` 和字符串 `"30"` 可能被判断为数值相等。
- 布尔值不进行数值归一化；列表、字典等结构化答案需要满足更严格的一致性要求。

要求仍然按照题干规定返回正确的数据类型，不要依赖系统的数值归一化机制来弥补格式问题。

如果返回结果与 `answer` 不一致，系统会报出 `ANSWER_MISMATCH`，导致打包失败。

**6. 参考程序还需要通过独立正确性检查**

需要特别强调：

**reference.py 的计算结果与 answer 一致，不代表参考程序一定正确。**

例如，题目要求先选择最新记录，再判断状态，但实际编写的参考程序采用了相反的操作顺序。

即使当前数据恰好使两种计算方式得到相同答案，程序仍然没有正确实现题意。

因此，课程后续还会检查：

- 参考程序是否完整实现题干要求。
- 是否存在筛选、排序、分组、聚合或其他处理逻辑错误。
- 是否遗漏影响计算结果的边界情况。
- 是否能够根据题干和数据独立复核标准答案。

Task Quality Gate 会尝试根据题面和数据独立求解，并与Task提供的 Reference 结果对账。

如果两者存在差异，需要进一步检查题目和参考程序，而不能简单地修改 `answer` 以通过校验。

**7. 提交前必须自查**

| 检查项目 | 要求                             |
| -------- | -------------------------------- |
| 文件名   | 必须为 `reference.py`            |
| 代码行数 | 最多 199 行                      |
| 语法检查 | Python 语法正确                  |
| 导入模块 | 仅使用 `pandas`、`decimal`       |
| 函数接口 | 必须定义可调用的 `reference(df)` |
| 数据输入 | 直接使用系统传入的 `df`          |
| 结果输出 | 使用 `return` 返回计算结果       |
| 文件操作 | 不读取或写出外部文件             |
| 危险调用 | 不使用被禁止的动态执行函数       |
| 运行时间 | 函数调用在 1 秒内完成            |
| 计算逻辑 | 完整符合 `task_statement`        |
| 标准答案 | 返回结果与 `answer` 一致         |
| 可复现性 | 相同数据和环境下得到相同结果     |

**最后强调：reference.py 是一份真正用于求解题目的参考程序，而不是保存标准答案的文件。**

必须根据题干编写正确的计算逻辑，直接处理系统传入的 DataFrame，并返回实际计算结果。

系统会同时检查代码是否合法、程序能否运行、结果是否与 `answer` 一致，以及参考程序是否真正符合题目要求。





#### <a id="agent-analysis"></a>

#### ⭐️⭐️⭐️ Agent：一道解决 Task 的程序 

Agent 是专门针对给定 Task 编写的求解智能体程序，文件为：

```
agent/
└── agent.py
```

Agent 需要根据题目要求，读取提供的 CSV 数据，完成相应的数据处理和计算，并按照题目规定返回结果。

##### agent.py 应该如何编写？

`agent.py` 是必须提交的智能体程序，最后会用于读取其他人设计的 Task，并根据题目要求和提供的 CSV 数据，独立计算最终答案。

强调自行设计 Agent 的解题策略，例如直接调用大语言模型、使用 pandas 处理数据，或者让模型分步骤分析并执行计算。

但必须遵守系统规定的函数接口、资源预算和运行要求。设计agent.py的目标是正确解决 Task，

**1. 文件格式与接口要求**

系统对 `agent.py` 有以下硬性要求：

| 检查项目    | 具体要求                                       |
| ----------- | ---------------------------------------------- |
| 文件名      | 必须命名为 `agent.py`                          |
| Python 导入 | 程序必须能够正常导入                           |
| 函数名称    | 必须定义可调用的 `run` 函数                    |
| 函数参数    | 必须恰好为 `run(task, df, llm)`                |
| 参数顺序    | `task`、`df`、`llm`，顺序固定                  |
| 参数数量    | 只能有这三个参数，不能增加或减少               |
| 最终输出    | 必须通过 `return` 返回最终答案                 |
| 文件数量    | 打包后的 `Agent_<学号>/` 中只能包含 `agent.py` |

特别注意：

- 不能把 `run` 改成 `solve`、`main` 等其他名称。
- 不能将 `df` 改成 `data`，或者将 `llm` 改成 `model`。
- 不能自行添加其他参数或默认值参数。
- 不允许只通过 `print()` 输出最终答案。
- Agent 必须能够在课程统一 Runner 中正常执行。

系统会按照固定接口调用Python代码程序，因此必须保持函数名称和参数完全一致。

**2. 必须定义 run(task, df, llm) 函数**

Agent 的基本接口如下：

```python
def run(task, df, llm):
    # 根据 task 理解题目要求
    # 使用 df 中的数据进行分析
    # 必要时通过 llm 辅助推理

    result = ...  # 最终计算结果
    return result
```

上述代码只用于说明函数结构，不是可以直接运行的完整 Agent。

三个参数的含义分别是：

| 参数   | 含义                                          |
| ------ | --------------------------------------------- |
| `task` | 系统提供的公开任务信息，用于理解题目要求      |
| `df`   | 系统读取 `data.csv` 后得到的 pandas DataFrame |
| `llm`  | 系统提供的大语言模型调用接口                  |

其中，`df` 已经由系统读取并传入，因此 Agent 不需要自行打开 `data.csv`。

`llm` 由课程统一提供的接口函数，不需要自行配置模型 API Key 或接入额外模型。

**3. Agent 应当能够解答不同类型的 Task**

与 `reference.py` 不同，Agent 不是只用于解答自己提交的一道题。

正式评测时，Agent 还需要面对其他人设计的未知任务。

例如：

- 有的 Task 要求筛选数据后计算总和。
- 有的 Task 要求排序、去重后统计数量。
- 有的 Task 要求处理缺失值或异常数据。
- 有的 Task 涉及时间、重复记录或多条件判断。
- 有的 Task 要求按照指定精度返回最终结果。

因此，Agent 应当能够根据不同题目的要求，动态决定解题步骤。

不能把某一道题的标准答案直接写进代码，也不能只根据固定字段名称返回预设结果。

**允许设计不同的智能体策略，但必须根据实际收到的题目和数据求解。**

**4. LLM 应当如何调用？**

系统已经提供了统一的大语言模型接口。

Agent 应通过以下方法调用模型：

```python
response = llm.complete(messages)
```

其中，`messages` 是消息列表，每条消息包含 `role` 和 `content`。

示例：

```python
messages = [
    {
        "role": "system",
        "content": "你是一个数据分析助手。"
    },
    {
        "role": "user",
        "content": "请根据题目要求分析数据并计算答案。"
    }
]

response = llm.complete(messages)
```

这里仅展示模型调用方式，实际 Agent 需要把本次任务要求和必要的数据内容提供给模型，或者使用 pandas 工具完成计算。

消息角色支持：

- `system`：规定模型的行为和任务。
- `user`：提供题目、数据和计算要求。
- `assistant`：保存模型之前的回复，用于多轮交互。

可以根据自己的策略设计单轮或多轮模型调用，但只能使用平台正式提供的模型接口和资源额度。

**5. Agent 的运行资源限制**

系统对每次 Agent 执行设置了统一资源预算。

| 资源项目          | 系统限制                                       |
| ----------------- | ---------------------------------------------- |
| 执行时间          | 90 秒，另有 10 秒启动宽限，总保护时间约 100 秒 |
| 内存              | 2048 MB                                        |
| 临时磁盘空间      | 512 MB                                         |
| 累计 Token        | 每次执行最多 10,000 Tokens                     |
| 单次 LLM 请求超时 | 75 秒                                          |
| LLM 超时重试      | 最多 1 次超时重试                              |

这些限制由系统统一管理，不能自行修改资源，一经发现，将不算作成绩。

特别注意：

- **Token 是整次任务的累计预算**，不是每轮模型调用都可以使用 10,000 Tokens。
- 多轮调用、工具执行和数据处理均会占用有限的执行时间。
- 单次 LLM 请求即使允许超时重试，也仍然受到整个 Agent 执行时间限制。
- 不建议将完整的大型 CSV 直接发送给模型，应根据题目需要合理读取、筛选或汇总数据。
- 不要在程序中设置不必要的长时间等待或无限循环。
- 避免产生大量无关中间文件或占用过多内存。

如果超出时间、内存、磁盘或 Token 限制，系统将终止本次执行。

**资源超限不会作为普通的工具观察结果返回给 Agent，让模型继续分析或重试。**

因此，需要在设计 Agent 时合理安排调用次数和计算过程。

**6. Agent 可以使用哪些工具？**

可以使用系统正式提供的数据、模型接口和运行能力，但不能通过额外信息来源获取标准答案。

| 能力或行为                         | 规范要求               |
| ---------------------------------- | ---------------------- |
| 读取公开任务要求                   | 允许                   |
| 处理系统传入的 DataFrame           | 允许                   |
| 使用 pandas 进行计算               | 允许                   |
| 调用平台提供的 `llm.complete()`    | 允许                   |
| 多轮模型推理                       | 允许，但受资源预算限制 |
| 使用本地数据筛选、排序、分组与聚合 | 允许                   |
| 自行接入第三方模型 API             | 不允许                 |
| 联网搜索题目答案                   | 不允许                 |
| 读取其他人的 Reference 或 Gold     | 不允许                 |
| 读取未授权的本地文件或私人数据     | 不允许                 |
| 修改原始任务数据以改变判分结果     | 不允许                 |
| 直接硬编码已知标准答案             | 不允许                 |

设计的智能体程序访问是在我们规定的运行范围之内，而不是任意访问文件、网络或额外服务。

设计智能体仍应遵守课程统一规定的数据访问范围、模型使用权限和评测要求。

**7. 如何使用系统当中提供的 Agent 模板？**

课程提供的标准 Agent 模板已经包含基于模型调用与 pandas 执行的基本解题流程。

模板要求模型每轮输出一种 JSON Action。

例如，执行 pandas 计算：

```json
{
  "action": "execute_pandas",
  "code": "result = int(df['amount'].sum()); print(result)"
}
```

或者提交最终答案：

```json
{
  "action": "final_answer",
  "answer": 30
}
```

在标准模板中：

- `execute_pandas` 用于执行数据处理代码。
- `final_answer` 表示模型已经得到最终结果。
- 执行结果会作为 Observation 返回，供模型继续判断。
- 如果生成的 Action 不是合法 JSON，模板会返回错误信息，供模型自行纠正。
- 模板对生成的 pandas 代码进行了基本安全检查，例如禁止直接导入模块以及使用 `open()`、`exec()`、`eval()`。
- 模板中的 pandas 执行环境主要提供 `df` 和 `pd` 两个对象。

**特别注意：上述 JSON Action 是标准模板内部使用的交互格式，并不是平台强制要求所有 Agent 必须采用的实现方式。**

可以在遵守 `run(task, df, llm)` 接口和系统资源限制的前提下，设计不同的智能体架构。

如果直接修改标准模板，建议保留已有的代码执行检查、异常处理和工具调用流程，避免因修改不当导致程序无法正常工作。

**8. 最终答案应该如何返回？**

Agent 必须根据 `task_statement` 要求返回最终结果。

例如：

| 题目输出要求           | 正确返回形式                                |
| ---------------------- | ------------------------------------------- |
| 返回整数               | `30`                                        |
| 返回保留两位小数的结果 | `"85.00"`                                   |
| 返回保留两位小数的结果 | `"0.30"`                                    |
| 返回字符串             | `"ACTIVE"`                                  |
| 返回布尔值             | `True` 或 `False`，以题目及评测格式要求为准 |

特别注意：

- 如果题目要求整数，应返回整数或符合判分规则的整数文本。
- 如果要求固定小数位数，应保留对应的小数位。
- 不要在最终答案中额外添加解释、单位或 Markdown 代码块，除非题目明确要求。
- 不要把模型的分析过程当作最终答案。
- 不要只在控制台打印结果，必须通过 `run()` 的返回值提交。

例如，题目要求输出整数 `30`，不应返回：

```
"经过统计，最终答案为30。"
```

应直接返回：

```
30
```

系统会将 Agent 的返回结果与标准答案进行比较。

对于普通数值，判分器允许一定的数值归一化；但仍应按照题目规定的输出格式返回答案。

**9. Agent 运行结果如何判定？**

系统主要将运行结果分为以下三类：

| 结果类型           | 含义                                               |
| ------------------ | -------------------------------------------------- |
| `completed`        | Agent 正常完成并返回正确答案                       |
| `analysis_failure` | Agent 正常返回答案，但与标准答案不一致             |
| `internal_error`   | 模型 API、资源限制、程序崩溃或其他运行异常导致失败 |

这里需要特别区分：

**Agent 算错题，与 Agent 程序运行失败，是两种不同情况。**

例如，Agent 正常运行，但把一道排序题的结果从 `30` 算成 `29`，属于解题错误。

如果 Agent 超时、内存超限、Token 超限，或者模型接口调用失败，则属于执行异常。

课程会根据不同结果分析 Agent 的解题能力和失败原因。

**10. Phase 1 与 Phase 2 的 Agent 使用规则**

Phase 1 提交的 `agent.py` 是正式参与 Exposure 测试的 Agent 版本。

因此：

- Phase 1 应提交能够正常运行的 Agent。
- 不要假设修改 Phase 2 的 `agent.py` 就会自动影响 Exposure 评测。
- Phase 1 和 Phase 2 的 `agent_id` 必须保持一致。
- `agent_id` 由 `metadata.json` 管理，格式为 `AGENT_<student_id>`。
- 正式打包时，`Agent_<学号>/` 目录中只能包含 `agent.py` 一个文件。

#### <a id="Person-info"></a>

#### ⭐️⭐️⭐️元信息管理文件填写 ⭐️⭐️⭐️ 

`metadata.json` 是 Task 和 Agent 的元信息管理文件，用于记录学号信息、任务编号、智能体编号以及希望考查的失败模式。

与 `task.json`、`data.csv`、`reference.py` 和 `agent.py` 不同，`metadata.json` 不负责描述题目内容或实现计算，而是用于标识提交对象，确保 Phase 1 和 Phase 2 的任务与智能体能够正确对应。

必须严格按照系统规定的字段名称和取值填写，不能自行增加、删除或修改字段。

#### **1. 文件位置与基本要求**

每个 Phase 目录中都必须包含一份 `metadata.json`。

```
workspace/
├── phase1/
│   ├── task.json
│   ├── data.csv
│   ├── reference.py
│   ├── agent.py
│   └── metadata.json
│
└── phase2/
    ├── task.json
    ├── data.csv
    ├── reference.py
    ├── agent.py
    └── metadata.json
```

特别注意：

- 文件名必须为 `metadata.json`。
- 文件内容必须符合标准 JSON 格式。
- 字段名称区分大小写，必须与系统规定完全一致。
- Phase 1 和 Phase 2 的字段要求不同，不能直接复制后不作修改。
- `metadata.json` 是学号信息及 Task、Agent 编号的唯一管理文件，不应在其他文件中另行维护与之冲突的身份信息。



#### **2. Phase 1 的 metadata.json 应该如何填写？**

Phase 1 必须且只能包含以下五个字段：

```json
{
  "workspace": "phase1",
  "student_id": "12561022",
  "task_id": "TASK_12561022",
  "agent_id": "AGENT_12561022",
  "hypothesized_failure_mode": "FM_AGGREGATION"
}
```

强调注明自己的学号，请在：

```json
metadata.json
```

中填写自己的学号在以下三个字段：

```json
  "student_id": "你的学号"
  "task_id": "TASK_你的学号",
  "agent_id": "AGENT_你的学号"
```

**学号要填写在student_id，task_id和agent_id**



五个字段分别有明确要求。

##### **（1）workspace：所属阶段**

用于说明当前文件属于哪个阶段。

Phase 1 必须填写：

```
"workspace": "phase1"
```

Phase 2 必须填写：

```
"workspace": "phase2"
```

不能填写其他名称，也不能将 Phase 1 的元信息误写成 `phase2`。

##### **（2）student_id：学号或唯一身份标识**

填写自己的学号，例如：

```
"student_id": "12561022"
```

要求：

- 长度为 2～32 个字符。
- 只能包含英文字母、数字和下划线。
- 不允许空格、中文、连字符或其他特殊符号。
- 必须与构建命令中提供的 `--student-id` 一致。
- 必须与最终提交包对应的学号标识一致。

建议直接填写自己的真实学号，不要使用示例中的编号提交。

##### **（3）task_id：任务编号**

用于唯一标识所提交的 Task。

必须采用：

```
TASK_<student_id>
```

例如，学号为 `12561022`：

```
"task_id": "TASK_12561022"
```

不能自行修改前缀，也不能使用其他编号。

##### **（4）agent_id：智能体编号**

用于唯一标识所提交的 Agent。

必须采用：

```
AGENT_<student_id>
```

例如：

```
"agent_id": "AGENT_12561022"
```

`task_id` 和 `agent_id` 是两种不同的编号，不要混用。

##### **（5）hypothesized_failure_mode：预期失败模式**

表示自己设计的 Task 主要希望考查 Agent 在哪个环节容易出错。

必须从系统规定的 14 种失败模式中选择一项，填写完整的 Failure Mode Key。

目前允许的类型包括：

- `FM_REQUIREMENT`
- `FM_SCHEMA`
- `FM_DATA_TYPE`
- `FM_FILTER_SORT`
- `FM_JOIN`
- `FM_AGGREGATION`
- `FM_TIME_TIMEZONE`
- `FM_MISSING_VALUE`
- `FM_OUTLIER_BOUNDARY`
- `FM_DUPLICATE_RECORD_HANDLING`
- `FM_PLANNING_DECOMPOSITION`
- `FM_VERIFICATION`
- `FM_NUMERICAL_PRECISION_ROUNDING`
- `FM_PROMPT_INJECTION`

例如，题目主要考查分组统计、求和或平均值计算，可以选择：

```
"hypothesized_failure_mode": "FM_AGGREGATION"
```

特别注意：

- 必须填写系统规定的完整名称。

- 不能自行新增失败模式。

- 不使用带数字编号的名称，例如 `FM06_AGGREGATION`。

- 如果一道题涉及多个错误环节，应选择最主要、最希望考查的失败模式。

- 失败模式表示希望考查的能力弱点，不代表可以故意提供错误题干、错误 Reference 或错误标准答案。

  

#### **3. Phase 2 的 metadata.json 应该如何填写？**

Phase 2 在 Phase 1 的五个字段基础上，必须额外增加一个字段：

```
review-comments_id
```

完整示例如下：

```json
{
  "workspace": "phase2",
  "student_id": "12561022",
  "task_id": "TASK_12561022",
  "agent_id": "AGENT_12561022",
  "hypothesized_failure_mode": "FM_AGGREGATION",
  "review-comments_id": "REVIEW_12561022"
}
```

其中：

- `workspace` 修改为 `phase2`。
- `student_id` 保持同一学号。
- `task_id` 必须与 Phase 1 完全相同。
- `agent_id` 必须与 Phase 1 完全相同。
- `hypothesized_failure_mode` 仍须使用合法的标准 Key。
- 新增的 `review-comments_id` 必须采用 `REVIEW_<student_id>` 格式。

**特别注意：Phase 2 是同一个 Task 和 Agent 的第二阶段版本，不是重新创建新的 Task 或 Agent。**

因此，不能将 Phase 2 的编号改成 `TASK_12561022_V2` 或 `AGENT_12561022_P2`。

系统会检查两个阶段的 `task_id` 和 `agent_id` 是否一致。



#### **4. 不允许增加或缺少字段**

`metadata.json` 使用严格字段校验。

Phase 1 只能有五个字段，Phase 2 只能有六个字段。

例如，下面的 Phase 1 写法不符合要求：

```json
{
  "workspace": "phase1",
  "student_id": "12561022",
  "task_id": "TASK_12561022",
  "agent_id": "AGENT_12561022",
  "hypothesized_failure_mode": "FM_AGGREGATION",
  "name": "张三"
}
```

其中 `name` 不是系统允许的字段，即使其他内容全部正确，也会导致校验失败。

同样，不能遗漏 `student_id`、`task_id`、`agent_id` 或 `hypothesized_failure_mode`。

**原则：系统规定几个字段，就填写几个字段，不要增加任何自定义信息。**



#### **5. 失败模式必须填写在 metadata.json 中**

按照当前 v10.1.18 及之后的契约，`hypothesized_failure_mode` 已从 `task.json` 迁移到 `metadata.json`。

因此，当前 `task.json` 应采用以下形式：

```json
{
  "description": "计算所有记录的金额总和。",
  "task_statement": "给定 data.csv，其中 amount 表示金额。计算全部记录的 amount 总和，最终返回一个整数。",

```

对应的失败模式写在 `metadata.json` 中：

```json
{
  "workspace": "phase1",
  "student_id": "12561022",
  "task_id": "TASK_12561022",
  "agent_id": "AGENT_12561022",
  "hypothesized_failure_mode": "FM_AGGREGATION"
}
```

特别注意：

- `task.json` 中不能再出现 `hypothesized_failure_mode`。
- `metadata.json` 中必须存在 `hypothesized_failure_mode`。
- 必须使用不带数字编号的标准 Failure Mode Key。
- 不要混用新旧版本的 JSON 格式。

如果仍在 `task.json` 中填写该字段，系统会报出 `TASK_JSON_FORBIDDEN_HYPOTHESIZED_FAILURE_MODE`。

如果 `metadata.json` 中缺少该字段，则会报出 `METADATA_MISSING_HYPOTHESIZED_FAILURE_MODE`。





#### **6. Phase 1 与 Phase 2 的身份信息必须保持一致**

系统要求两个阶段属于同一个人操作(两个阶段学号务必一致)、同一 Task 和同一 Agent。

| 检查项目             | 要求                                          |

### 数据挖掘课程小组作业

#### 作业目的与总体要求

本次课程大作业考核采用小组项目作业形式，不再安排期末笔试。各小组需要围绕实际应用场景，自主选择数据挖掘案例，完成数据分析、算法应用、分布式计算方案设计以及算法可视化演示，综合考查对数据挖掘基本理论、算法原理和大数据处理技术的理解与应用能力。

本次作业不仅要求掌握数据挖掘算法的基本原理，更强调将算法应用于实际问题的能力，以及通过动画、可视化等形式展示算法运行过程的能力。

每个小组需要独立完成 **两个数据挖掘案例**。每个案例均应包含以下三个部分：

1. 数据分析案例描述；
2. 算法应用方案与算法流程描述；
3. 海量数据下大数据分布式计算解决方案。

两个案例依次组织，分别形成完整的分析、算法应用和分布式计算方案。

最终成果应体现数据挖掘算法从实际问题提出、数据处理、算法运行到结果分析，以及从单机计算向分布式计算扩展的完整过程。
